# game3d-server

Автономный консольный сервер многопользовательского режима игры **Game3D**.

В этой ветке находится только сервер. Клиент (игра) — отдельная программа из
основной ветки репозитория Game3D: сервер с ней не линкуется и не собирается,
они общаются только UDP-датаграммами по протоколу, зафиксированному ниже.

## Сборка

Нужны CMake 3.20+ и компилятор C11 (GCC/Clang на Linux, Visual Studio на
Windows). OpenGL, GLFW и stb не требуются, поэтому сервер собирается на
выделенной машине без графики.

```sh
cmake -S . -B build
cmake --build build --config Release
```

Windows — то же самое из **Developer PowerShell for VS**.

Опция `GAME3D_SANITIZERS=ON` включает AddressSanitizer и
UndefinedBehaviorSanitizer (GCC/Clang). На Windows линкуется Winsock
(`ws2_32`), на POSIX — pthread (поток чтения команд stdin).

## Запуск

```sh
./build/game3d-server --name "Ночная смена" --map arena.tfm --max-players 8
```

Сервер полностью CLI: вся настройка — флагами командной строки, события
пишутся в stdout, команды управления читаются со stdin. Он работает и в
интерактивном терминале, и под `nohup`/systemd с перенаправленным логом
(закрытый stdin просто отключает команды, не останавливая сервер).

| Флаг | Описание |
| --- | --- |
| `-p, --port <порт>` | UDP-порт, 1..65535 (по умолчанию `27015`) |
| `-b, --bind <адрес>` | адрес привязки сокета (по умолчанию `0.0.0.0`; IPv6 — `--bind ::`) |
| `-n, --name <имя>` | имя в списке серверов, до 63 байт UTF-8 (по умолчанию `Game3D Server`) |
| `-m, --map <карта>` | карта для подключившихся клиентов, до 255 байт печатного ASCII |
| `-M, --max-players <N>` | максимум игроков, 1..64 (по умолчанию 16) |
| `-t, --timeout <сек>` | тайм-аут сессии без пакетов, минимум 1 (по умолчанию 30) |
| `-v, --verbose` | логировать каждую датаграмму |
| `-q, --quiet` | печатать только ошибки |
| `-h, --help` | справка по параметрам |
| `-V, --version` | версия сервера |

Длинные флаги пишутся и через пробел, и через `=` (`--port=28000`); короткие
можно сцеплять (`-vq` нельзя — это взаимоисключающие уровни лога).

Пустая карта (`--map ""`, значение по умолчанию) означает: каждый клиент играет
на выбранной у себя в меню карте. Непустая — при подключении клиент
переключается на указанную карту.

Как клиенты находят сервер: игра рассылает UDP-broadcast `[1]` на
`255.255.255.255:27015` (поэтому сервер в LAN обнаруживается без настройки) и
опрашивает адреса из файла `servers.txt` рядом с клиентом:

```text
# servers.txt у клиента: один адрес на строку, порт после «:»
203.0.113.17:27015
192.168.1.40:28000
```

## Команды

Во время работы сервер читает команды со stdin:

| Команда | Действие |
| --- | --- |
| `help` | список команд |
| `status` | аптайм, адрес, имя, карта, игроки, `tick` |
| `list` | подключённые игроки: ID, адрес, позиция, время без пакетов |
| `kick <id>` | отключить игрока по числовому ID из `list` |
| `quit` | остановить сервер (также `exit`, `shutdown` или Ctrl+C) |

## UDP-протокол

Спецификация перенесена из README игры Game3D — это контракт, который
реализует сервер.

Каждое сообщение — **ровно одна UDP-датаграмма** и начинается с `[num]` —
одного беззнакового байта. Числа `u32` записываются в сетевом порядке байтов
(big-endian), координаты и векторы — `f32`, IEEE-754 binary32, также
big-endian. `name` — UTF-8-строка, а `map` — строка из **печатного ASCII**
(`0x20`…`0x7e`); обе завершены байтом `0`. Поля `max_players` и `players` —
по одному `u8`; `tick` — `u32`. Квадратные скобки ниже обозначают
последовательные байты полей, а не текстовые символы.

Браузер серверов у клиента принимает ответ `[1]` только при точном размере
`7 + strlen(name) + 1 + strlen(map) + 1` байт: после нуля, завершающего
`map`, не должно быть лишних данных. Ответ отбрасывается, если `map`
содержит не-ASCII байт, строка не заканчивается нулём, имя/карта не
помещаются в ограничения (63/255 байтов) или `players > max_players`. Так в
список не попадают случайные UDP-пакеты и некорректные серверы.

| `num` | Датаграмма клиента | Ответ сервера и действие |
| --- | --- | --- |
| `1` | `[1]` | `[1][max_players][players][tick][name][0][map][0]`. Клиент показывает сведения и затем посылает запрос `2`. |
| `2` | `[2]` | Если `players >= max_players`, сервер отдаёт ровно `[2]`. Если `players < max_players`, он создаёт новый случайный `u32` ID, которого нет у других сессий, и отдаёт `[2][id]`. |
| `3` | `[3][id][x][y][z][lx][ly][lz]` | `id` — `u32` из успешного ответа `2`; `x`, `y`, `z` — позиция, `lx`, `ly`, `lz` — вектор взгляда. Сервер проверяет ID, сохраняет состояние игрока и отвечает ровно `[3]`. |
| `4` | `[4][id]` | `id` — тот же `u32` из ответа `2`. Сервер проверяет ID и возвращает `[4]` с данными всех видимых игроков: запись игрока — `[x][y][z][lx][ly][lz]`, соседние записи разделяет `[0]`; пустой список — просто `[4]`. Клиент также принимает завершающий `[0]` после последней записи. |
| `5` | `[5]` | Сервер удаляет ID, связанный с этой UDP-сессией, завершает сессию игрока; ответа не требуется. |

ID из ответа `2` передаётся в каждом пакете состояния `3` и запроса видимых
игроков `4`; сервер обязан сверять его с активной сессией. Пакет выхода `5`
остаётся без аргументов и завершает сессию по UDP endpoint. При повторе `[2]`
от уже зарегистрированного endpoint (UDP может потерять ответ) сервер
возвращает тот же ID, а не создаёт второго игрока.

Клиент повторяет потерянные запросы `1` и `2` до пяти раз, отправляет
состояние `3` на каждом шаге физики (60 Гц) и запрашивает видимых игроков `4`
до 10 раз в секунду. При выходе из сетевой партии или закрытии игры он
посылает `[5]` и закрывает UDP-сокет. UDP не гарантирует доставку `[5]`,
поэтому сервер очищает давно неактивные сессии по тайм-ауту (`--timeout`).

## Поведение сервера сверх таблицы

- `tick` в ответе `[1]` — время работы сервера в тиках по 1/60 с;
- `players` — число активных сессий; сессия живёт от успешного `[2]` до `[5]`,
  `kick` или тайм-аута;
- повторный `[2]` с того же endpoint возвращает тот же ID;
- `[3]` и `[4]` с неизвестным или чужим ID молча игнорируются;
- в ответе `[4]` перечисляются все остальные игроки с известным состоянием —
  не больше 58 записей, чтобы датаграмма не превышала типичный MTU 1500;
- датаграммы неверной длины и с неизвестным номером игнорируются целиком.
